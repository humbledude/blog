무료 클라우드에 게임 서버 올려보기 - CPU보다 서버가 어디 있느냐가 문제였다

돌아서면 까먹는다
2026-10-26
개발
WebSocket, 게임 서버, 무료 서버, 벤치마크, 클라우드

작은 멀티플레이 게임을 만들어 보고 있다. 폭탄 놓고, 도망가고, 못 도망가면 죽는 그런 게임이다.

아직 엄청난 게임은 아니다. 그런데 무료 서버를 어디에 올리느냐에 따라 움직이는 느낌이 제법 달랐다.

처음엔 서버가 구려서 그런가 싶었다. 무료니까 뭐.. 싶기도 하고.
그래도 느낌으로만 서버 탓을 하면 억울할 수 있으니, 같은 게임을 여기저기에 올리고 직접 재보기로 했다.

결론부터 말하면 이번 게임 규모에서는 CPU보다 서버 위치와 네트워크 경로의 영향이 훨씬 크게 보였다.
그리고 늘 그렇듯, ‘무료’라는 글씨 뒤에는 읽어야 할 작은 글씨가 많았다..

뭘 올렸나

클라이언트는 Phaser + TypeScript이고, 서버가 이동과 폭탄, 피격을 판정한다. 클라이언트에는 로컬 이동 예측도 있다.

처음에는 Cloudflare Durable Objects로 만들었다. 그다음 같은 게임 코어를 Node.js WebSocket 서버에서도 돌릴 수 있게 분리하고, Docker 이미지로 배포했다.

이번에 실제로 올려본 곳은 다음과 같다.

서비스 실제 테스트 위치 실행 방식
Cloudflare Workers + Durable Objects 실제 DO 실행 리전은 확인하지 못함 서버리스 상태 객체
Render Free 싱가포르 Node.js + Docker
Oracle Cloud Always Free Micro 오사카 Node.js + Docker
Google Cloud e2-micro 서울 asia-northeast3-a Node.js + Docker

Oracle은 가입할 때 한국 리전을 선택할 수 없어서 오사카로 진행했다. 그래서 Oracle 한국 리전의 핑은 이번에 테스트하지 못했다.

이건 ‘Oracle에 한국 리전이 없다’는 뜻은 아니다. 내 가입 과정에서 선택할 수 없었다는 이야기다. Always Free Compute는 홈 리전에서 만들어야 한다는 제약도 있어, 오사카 홈 리전 계정으로 한국에 하나 더 만들면 똑같이 무료라고 생각하면 안 된다.[3]

여기서 말하는 핑은 ICMP ping이 아니다

게임 WebSocket으로 ping 메시지를 보내고 pong이 돌아올 때까지의 시간을 쟀다. 앱 수준의 왕복 지연, 즉 RTT다.

전송·수신 시각 모두 같은 클라이언트 시계로 재므로 서버와 PC의 시계가 얼마나 맞는지는 관계없다.

서버는 이 pong을 다음 게임 틱까지 기다렸다가 보내는 게 아니다. 따라서 RTT가 크다고 바로 ‘게임 로직 처리 속도가 느리다’고 결론 내릴 수는 없다. 네트워크와 서버의 메시지 처리 지연이 함께 들어간 값이다.

입력의 seq가 서버 스냅샷에서 확인될 때까지 걸린 입력 ACK 지연도 별도로 기록했다. 이건 네트워크에 다음 틱·스냅샷을 기다리는 시간까지 더해진다. 누적 ACK이므로 중간 입력 하나하나가 모두 별도의 시뮬레이션 단계에서 실행됐다는 뜻은 아니다.

4명이 1분 동안 돌아다니게 했다

사람 네 명을 붙잡고 1분씩 똑같이 움직이게 하기는 귀찮다. 그래서 실제 WebSocket으로 접속하는 봇을 만들었다.

  • 같은 Mac mini에서 각 서버에 접속
  • 모든 봇이 입장한 뒤 공통 60초 구간 측정
  • 계속 방향을 바꾸며 이동하고 주기적으로 폭탄 설치
  • 죽으면 자기 캐릭터만 부활
  • 플레이어별 RTT, ACK 지연, 권위 좌표 변화, 서버 틱 지표 기록
  • Oracle과 GCP는 SSH로 컨테이너 CPU·메모리도 약 2초 간격 수집
  • 실제 사용자가 있는 방이면 테스트 중단

좌표가 실제로 바뀌는지도 확인했다. 벽에 머리 박고 1분 동안 ‘열심히 움직이는 중’이라고 우기면 부하 테스트가 아니라 벽 테스트니까..

단, 봇은 게임 화면을 그리지 않는다. 실제 네트워크·서버 프로토콜 테스트이지, 휴대폰 그래픽 성능이나 브라우저 FPS 테스트는 아니다. 봇마다 행동 시작을 조금씩 어긋나게 했고, 서버 반응에 따라 움직이므로 같은 seed라도 완전히 같은 경로를 걷지는 않는다.

4명 결과: 서울은 가까웠다

Node.js 서버는 같은 게임 빌드 v1.0.3를 사용했다. Oracle과 GCP에는 같은 AMD64 Docker 이미지를 올렸다.

모바일에서는 넓은 표를 좌우로 밀어서 볼 수 있다.

서버 RTT 중앙값 RTT p95 입력 ACK p95 컨테이너 CPU 평균 컨테이너 메모리 관측 최대
Oracle Micro / 오사카 42.21ms 44.13ms 70.55ms 2.59% 135.18MiB
Render Free / 싱가포르 113.91ms 127.28ms 145.59ms 미측정 미측정
GCP e2-micro / 서울 5.69ms 6.78ms 36.10ms 2.92% 145.25MiB

p95는 측정값의 약 95%가 그 값 이하라는 뜻이다. CPU의 100%는 코어 하나를 다 쓴 상태를 기준으로 했고, 메모리는 JS heap만이 아니라 캐시 등을 포함한 cgroup 사용량이다.

각 서비스는 같은 시각에 동시에 잰 것이 아니라 순차적으로 측정했다. ISP 경로, 시간대, 공유 호스트 상태까지 통제한 연구실 실험은 아니다. 서비스 전체의 평균 성능이나 순위를 뜻하지 않는다.

그래도 이 테스트에서 서울의 RTT가 낮았다는 건 꽤 분명하다. 오사카 Micro도 CPU가 모자라서 허덕이는 모습은 아니었다.

내가 폰으로 Oracle에 접속했을 때는 70~100ms 정도도 보였다. 위 표는 Mac에서 측정한 값이다. PC와 폰, Wi-Fi와 모바일 통신의 결과를 한 통에 넣으면 안 된다.

Cloudflare는 어땠나

앞선 별도의 짧은 비교에서는 Cloudflare RTT 중앙값이 53ms, 범위는 42~72ms였다. 약 30초 동안 12번 읽은 값이다. 같은 비교의 Render는 중앙값 119ms였다.

하지만 이때는 4명 능동 이동 부하 테스트가 아니고, 당시 게임 빌드와 연결 수도 이후 테스트와 같지 않았다. 그래서 위 4명 표에 슬쩍 끼워 넣지는 않았다. Cloudflare DO가 실제 어느 리전에서 실행됐는지도 확인하지 못했다.

‘Cloudflare니까 무조건 한국 엣지에서 게임도 돈다’고 가정하면 안 된다는 정도만 기억해두자.

인원을 늘리면 CPU가 부족해질까

현재 게임은 방당 4명이고, 허용된 방도 4개뿐이다. 게임 규칙을 바꾸지 않고 여러 방에 나눠 넣었다.

  • 4명: 30Hz 방 하나
  • 8명: 30Hz 방 두 개
  • 12명: 위 두 방 + 20Hz 방 하나
  • 16명: 30Hz 방 두 개 + 20Hz 방 두 개

12·16명은 틱레이트 혼합이다. 30Hz 단일 방에 16명을 넣은 결과가 아니다. 각 단계는 따로 1분씩 측정했다.

총 플레이어 Oracle RTT p95 Oracle CPU 평균 서울 GCP RTT p95 서울 GCP CPU 평균
4 44.13ms 2.59% 6.78ms 2.92%
8 44.50ms 3.92% 7.45ms 3.11%
12, 혼합 47.77ms 4.45% 7.60ms 3.81%
16, 혼합 46.97ms 5.80% 6.96ms 4.09%

Oracle과 GCP는 전 단계에서 연결 끊김과 버린 시뮬레이션 시간(droppedDebtMs)이 0이었다. 30Hz 방에서 서버가 보고한 rolling 틱 간격 p95의 관측 최댓값도 두 서비스 모두 35ms 이내였다.

16명까지 별문제 없었다고 ‘최대 동접 16명 서버’라고 부르면 안 된다. 성능 한계가 아니라 지금 앱의 인원 제한에 먼저 도달했다.

또 Micro는 공유 CPU다. 1분 동안 잘 돌았다고 하루 종일 CPU를 밀어붙여도 똑같을 거라는 보장은 없다.

Render는 왜 4명에서 멈췄나

상승 중단 기준을 미리 정했다. 그중 하나가 ‘서버가 보고한 틱 간격 p95가 목표 간격의 1.5배 이내일 것’이었다. 30Hz에서는 50ms다.

Render는 4명 테스트를 60초 완료했고 연결 끊김과 droppedDebtMs도 0이었다. 다만 서버가 보고한 rolling 틱 간격 p95가 한때 60ms까지 올라가 이 기준에서 멈췄다.

이건 전체 1분의 틱 p95가 60ms였다는 뜻도 아니고, Render 최대 수용 인원이 4명이라는 뜻도 아니다. CPU·메모리를 직접 읽지 못했으니 원인을 CPU 부족으로 확정할 수도 없다.

첫 준비 확인에서는 4초 health 요청이 시간 초과됐다. 이후 정상 응답을 확인하고 부하를 넣었다. Render Free는 무입력 15분 후 휴면하고 다시 깨어나는 데 약 1분이 걸릴 수 있으니, 콜드 스타트와 깨어난 뒤의 성능도 분리해야 한다.[5]

그래서 어디까지 무료인가

아래는 2026년 10월 26일 공식 안내 확인 기준이다. 무료 정책은 바뀔 수 있다. ‘VM 무료’와 ‘공개 서비스 운영비 전체 0원’은 다른 말이다.

후보 무료로 주는 것 주의할 것 이번에 확인한 범위
Oracle Always Free AMD Micro 최대 2대, A1은 합계 2 OCPU·12GB 상당의 월 무료 할당, 부팅·블록 볼륨 합계 200GB 홈 리전 제약, 자리 부족, 유휴 자원 회수 가능 오사카 AMD Micro 실행
Render Free 워크스페이스당 월 750시간의 Free 인스턴스 시간 15분 무입력 휴면, 대역폭·빌드 한도 별도 싱가포르 Free 실행
Google Cloud Free Tier 미국 지정 3리전의 e2-micro 월 무료 사용량, 표준 영구 디스크 30GB-month 서울은 대상 아님. 공인 IPv4·전송료는 별도 확인 서울 유료 리소스를 크레딧으로 비교
Cloudflare Workers + Durable Objects Free 플랜에 요청·활성 시간 등의 일일 무료 한도 VM 한 대를 주는 방식이 아님. 틱 루프와 열린 연결의 수명 관리 중요 짧은 RTT 비교 후 배포 삭제
네이버 클라우드 Micro 한국 Micro 서버 1대, 신규 결제 수단 등록 월부터 1년 무료 공인 IP 별도 과금, 1년 후 미반납 시 유료 전환 공식 조건 확인만, 실행 안 함

각 항목의 공식 근거는 다음과 같다.

  • Oracle 무료 자원.[3]
  • Render 무료 서비스.[5]
  • GCP 무료 범위와 네트워크 요금.[6][8]
  • Cloudflare Durable Objects 요금·무료 한도.[7]
  • 네이버 무료 기간·공인 IP·한국 Micro 조건.[1][2][4]

Oracle: 예전 무료 한도를 그대로 믿으면 안 된다

현재 공식 문서의 A1 무료 할당은 월 1,500 OCPU-hours, 9,000 GB-hours, Always Free 기준 2 OCPU·12GB 상당이다. 예전 글에서 보던 4 OCPU·24GB와 다르니 최신 문서를 확인해야 한다. 춘천은 무료 A1 생성 제외도 명시돼 있다.[3]

이번에는 고정 사양을 이해하기 쉬운 AMD Micro부터 써봤다. A1은 무료 자리가 있는지 확인·배포한 결과가 아직 없으므로 성능 표에도 넣지 않았다.

Google: 서울은 무료 리전이 아니었다

e2-micro Free Tier 리전은 미국 오리건 us-west1, 아이오와 us-central1, 사우스캐롤라이나 us-east1이다. 서울은 여기에 없다.[6]

e2-micro에 공인 IP를 못 붙인다는 뜻도 아니다. 실제 이번 서울 VM도 공인 IPv4로 직접 접속했다. 다만 공인 IPv4는 별도 과금 항목이라, 무료 VM이라고 해서 모든 비용이 없어지는 건 아니다.[8]

남아 있는 크레딧으로 서울만 짧게 비교했다. 크레딧 만료가 가까워 지속 개발 환경으로 삼지는 않았다. 테스트 뒤에는 VM뿐 아니라 부팅 디스크, 테스트용 방화벽·서브넷·VPC까지 삭제하고 부재를 확인했다. 실제 청구·크레딧 차감액은 아직 확인하지 못했다.

Cloudflare: 무료가 없다는 게 아니라 실행 시간을 봐야 했다

현재 Durable Objects Free 플랜에는 하루 요청 100,000건, duration 13,000 GB-s 등의 한도가 있다. Free 플랜에서 해당 한도를 넘으면 그 종류의 작업이 오류로 실패한다. 유료 플랜의 초과 사용 과금과 구분해야 한다.[7]

내 구현은 마지막 연결이 끊기면 게임 루프를 멈추지만, 연결된 채 가만히 있는 사람이나 죽은 캐릭터가 남아 있으면 루프가 계속 돈다. 접속자 0명과 실제 플레이를 안 하는 상태는 다르다.

계속 틱을 돌리는 실시간 게임은 WebSocket 연결만 유지하면서 잠들 수 있는 앱과 비용 패턴도 다르다. Cloudflare 문서 역시 활성 상태 또는 hibernation이 불가능한 상태의 duration을 설명한다.[7]

그래서 이번에는 무료 한도 관리 정책을 더 설계하기 전에 공개 배포부터 내렸다. 실제 초과 요금이 발생했다고 확인한 것은 아니다. ‘Cloudflare는 안 쓰는 동안에도 무조건 과금된다’는 결론도 아니다.

국내 사업자는 없나 했더니

네이버는 한국 Micro 1년 무료가 있었다. 다만 공인 IP까지 포함한 무기한 0원 서버는 아니었다.[1][2][4]

이런 작은 게임을 오래 굴리려면 결국 다음을 같이 봐야 한다.

  • 서버 본체의 무료 기간과 CPU·메모리
  • 공인 IP, 디스크, 아웃바운드 트래픽
  • 접속자가 없을 때 정지 가능한지
  • 휴면 복귀를 플레이어가 기다려줄 수 있는지
  • 무료 기간이 끝나면 자동 과금되는지

무료 서버라는 큰 글씨만 보고 누르면, IP라는 작은 친구가 옆에서 계산기를 두드릴 수 있다..

이번 결론

이번에 필요한 건 엄청난 CPU가 아니었다. 작은 서버로도 게임 로직은 충분히 돌아갔고, 한국에서 가까운 경로의 서버를 고르는 게 지연을 줄이는 데 더 중요했다.

그렇다고 ‘게임 서버는 무조건 가까우면 끝’은 아니다. 큰 맵, 복잡한 AI, 단일 방의 많은 플레이어, 장시간 부하, 패킷 손실은 아직 테스트하지 않았다. 가까운 공유 서버가 바빠지면 당연히 문제가 생길 수 있다.

당장 남은 과제는 더 좋은 CPU를 고르는 것보다, 가까운 서버를 얼마나 싸게 유지하고, 아무도 안 할 때 얼마나 얌전히 쉬게 만들 것인가 쪽에 가까워 보인다.

공짜 서버 찾으러 다니다가 지리 공부를 했다. 역시 개발은 종합 과목이다..

측정 데이터

이 글의 수치는 로컬에 보존한 실행 로그·집계 JSON에서 가져왔다. 공개용 파일에서는 계정, VM 주소, 플레이어 식별자와 SSH 관련 정보를 제외했다.

  • 서버·단계별 집계 JSON (텍스트 파일)
  • 플레이어별 지연 CSV

모든 환경을 같은 시각·같은 하드웨어로 통제한 벤치마크가 아니므로, 서비스 간 일반적인 우열을 주장하는 자료로 쓰지는 말자.
